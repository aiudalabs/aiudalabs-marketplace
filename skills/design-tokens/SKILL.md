# Design Tokens

Produce one tokens file that is the single source of truth for the brand's visual values, prove it is valid, and export it to the format the product uses.

## Inputs

- The decided values: color ramps and roles, font families, type scale, spacing, radius. If these are not decided yet, decide them first. This skill records decisions; it does not make them.
- Where the tokens will be used: a website, an app, a design tool.
- Whether there is a dark theme.

## Workflow

### 1. Structure the file in layers

Follow [references/token-architecture.md](references/token-architecture.md). Use two layers to start:

- **Primitive tokens** hold raw values: `color.primary.600`, `space.4`.
- **Semantic tokens** name a purpose and point to a primitive: `color.action.default` is `{color.primary.600}`.

Product code uses semantic tokens only. Add a component layer later, when a real component needs its own override.

### 2. Write the tokens

Start from [assets/example.tokens.json](assets/example.tokens.json) and replace every value. The values in it are placeholders that show the structure.

The format rules that are easy to get wrong are in [references/format-cheatsheet.md](references/format-cheatsheet.md). The two most common mistakes:

- A color is an object with `colorSpace` and `components`, not a hex string. Keep the hex in the optional `hex` field.
- A dimension is an object with `value` and `unit`, where the unit is `px` or `rem`.

Name the file with the `.tokens.json` extension.

### 3. Validate

```bash
node scripts/validate-tokens.mjs brand.tokens.json
```

It exits with code 1 and lists every problem: invalid names, missing types, malformed values, references to tokens that do not exist, circular references, and a `hex` that does not match its `components`. Fix every error before exporting.

The script warns, without failing, about the parts of the format it does not check in depth. They are listed at the top of the script and in the cheatsheet.

### 4. Export

```bash
node scripts/export-tokens.mjs brand.tokens.json --prefix brand > brand.css
node scripts/export-tokens.mjs brand.tokens.json --format json > brand.flat.json
```

In CSS, references become `var()` calls, so overriding a primitive updates everything that points to it. `--prefix` namespaces the variables. `--selector` changes the rule the variables are declared in.

### 5. Add the dark theme

Keep dark theme overrides in a second file that redefines only the semantic tokens that change, then export it under a different selector:

```bash
node scripts/export-tokens.mjs brand.dark.tokens.json --prefix brand --selector '[data-theme="dark"]' >> brand.css
```

The dark file must be valid on its own, so it needs the primitives its references point to. The simplest way is to copy the primitive groups into it.

### 6. Hand over

Deliver the tokens file, the exported files, and a short note that says which tokens product code may use (semantic) and which it may not (primitive).

## Output

1. `brand.tokens.json`, and `brand.dark.tokens.json` if there is a dark theme
2. The validator output showing zero errors
3. `brand.css`, or the format the product needs
4. The usage note

## Limits

- The exporter writes CSS custom properties and flat JSON. For other targets, such as native platforms or a framework's theme file, map the flat JSON yourself or use a build tool such as Style Dictionary. Check that the tool's version supports the 2025.10 format before relying on it.
- The format has no built-in way to express themes in a single file, which is why the dark theme lives in its own file here.

## Quality checks

- [ ] The validator reports zero errors
- [ ] No hex value appears in the semantic layer; semantic tokens are references
- [ ] Every value came from a recorded brand decision, with no placeholder left from the example
- [ ] Token names describe purpose in the semantic layer (`color.action.default`), not appearance (`color.blue-button`)
- [ ] The exported file was generated by the script, not edited by hand
